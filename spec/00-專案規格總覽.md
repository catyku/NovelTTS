# novel-tts 專案規格總覽

更新日期：2026-11-16
專案位置：`~/GitHub/novel-tts`
狀態：**規格確認階段**（本文件為實作前的唯一依據，實作中若有偏差需回寫本文件）

## 1. 專案目標

將小說純文字內容，交由 AI 模型分析並分解成「角色（人聲）× 段落（台詞／旁白）」，
再呼叫 AI TTS 模型逐段發聲，最終輸出可下載的聲音檔（每段音檔、章節合併檔、整本 ZIP）。

## 2. 技術棧定案

| 項目 | 決策 | 備註 |
|---|---|---|
| 後端框架 | Spring Boot 4.1.2 | 2026-10-22 釋出，Spring Framework 7.0.10 / Hibernate 7.4.13 / PG driver 42.7.14 |
| JDK | 25（本機 25.0.5） | Spring Boot 4 baseline 為 Java 17+ |
| 建置 | Maven 3.9.9 | |
| 資料庫 | PostgreSQL 17.12 | 本機容器 `noveltts-pg` |
| ORM / 遷移 | Spring Data JPA + Flyway | `db/migration/V1__init_schema.sql` |
| AI 分析 | OpenRouter `POST /api/v1/chat/completions` | WebClient |
| AI TTS | OpenRouter `POST /api/v1/audio/speech` | 模型 `google/gemini-3.8-flash-tts` |
| 音訊後處理 | ffmpeg / ffprobe（本機已裝） | PCM → MP3、章節合併、時長量測 |
| 前端 | Thymeleaf + Spring Security（Session-based） | 管理介面四頁 |
| 容器 | Podman 5.4.2 rootless（本機無 Docker daemon） | 部署檔寫成標準 `docker-compose.yaml`，本機以 `podman-compose up -d` 執行 |

### 2.1 為什麼用 Podman 而非 Docker

本機 `192.168.0.197` 沒有 Docker daemon（`/var/run/docker.sock` 不存在），
但已安裝 **Podman 5.4.2（rootless, cgroup v2）** 與 `podman-compose`。
Podman 對 `docker-compose.yaml` 與 `docker` CLI 語法高度相容，因此：
- 部署檔維持 `docker-compose.yaml` 標準格式（可無縫搬到有 Docker 的環境）
- 本機開發一律 `podman-compose up -d` / `podman exec`，**不需安裝 Docker、不需 sudo**

### 2.2 既有環境事實（實測）

- PostgreSQL 容器：`noveltts-pg`，`127.0.0.1:5432`，db/user=`noveltts`，password=`noveltts_dev_pwd`，volume `noveltts_pgdata`
- 本機 `ffmpeg` / `ffprobe` 存在；記憶體 3.9GiB / 4 核 → 併發上限設 3
- 遠端 `192.168.0.172` 僅有 MySQL(3306)，**無 PostgreSQL**

## 3. 系統架構

```text
小說 TXT / 貼上文字
      │
      ▼
[章節切分] 規則式：偵測「第一章 / Chapter N / 中文數字標題」等
      │
      ▼
[AI 分析]  OpenRouter chat/completions → 嚴格 JSON（segments 陣列）
      │      失敗 → 帶錯誤訊息重試 1 次 → 仍失敗標 job FAILED
      ▼
[角色去重合併] 依 character_name + aliases 合併
      │
      ▼
[dialogue_segment 落庫] + [character 落庫]
      │
      ▼
[音色指派]  人工於介面指派（AI 可給建議 voice_id）→ character.tts_voice_id
      │
      ▼
[TTS 合成]  依「連續多角色」分組 → multi-speaker input 陣列 → 單次請求
      │      落地 PCM → ffmpeg 轉 MP3 → 量測 duration_ms
      ▼
[audio_file 記錄]  provider / model / voice_id / generation_id / duration / size
      │
      ▼
[章節合併檔]  ffmpeg concat → [整本 ZIP]
```

## 4. 模組結構（Yongkang 風格）

```text
novel-tts/
├─ spec/                       # 本目錄：規格文件（實作前唯一依據）
├─ db/migration/
│  └─ V1__init_schema.sql      # Flyway 遷移腳本
├─ app/                        # domain + service + AI client + TTS client + JPA
│  └─ src/main/java/com/noveltts/
│     ├─ domain/entity/        # JPA Entity
│     ├─ domain/repository/     # Spring Data JPA
│     ├─ service/              # NovelService / AnalysisService / TtsService / ExportService
│     ├─ ai/                   # OpenRouterClient / PromptBuilder / SegmentParser
│     ├─ tts/                  # TtsClient / AudioAssembler / PcmToMp3Converter
│     ├─ config/               # properties / SecurityConfig / WebClientConfig
│     └─ job/                  # 非同步 job 執行與進度回報
├─ web/                        # Controller + Thymeleaf + Security
│  └─ src/main/resources/templates/  (settings / novels / characters / segments)
├─ WebEnv/                     # docker-compose.yaml + .env.example + postgres init
└─ README.md                   # 本地啟動與開發流程
```

`app` 與 `web` 分離的原因：`web` 只負責 HTTP 呈現與權控，所有業務規則與外部服務呼叫在 `app`，
未來若要加 CLI 排程器或另一個 API 端，可直接重用 `app`。

## 5. 設定介面（可設定 = 資料庫 + 頁面）

設定不寫死在 `application.yml`，而是落在 `ai_provider_config` / `ai_model_setting` / `tts_voice` 三張表，
由 `/settings` 頁面維護。這樣：

- 換 provider（OpenRouter base_url、額外 headers）不需改 code、不需重編譯
- 分析模型與 TTS 模型可獨立指定（不同 model_id、不同 temperature、額外 params）
- 音色庫可擴充（新增 voice_id + style_desc），角色指派時直接選

API Key 以 AES-GCM 加密後存 DB，主金鑰由環境變數 `NOVELTTS_MASTER_KEY` 提供（不入庫、不進版控）。

## 6. 非功能需求

| 項目 | 要求 |
|---|---|
| 併發 | TTS 併發上限 3（`Semaphore`），避免 OpenRouter 429 與記憶體壓力 |
| 重試 | 429 / 5xx 指數退避（1s→2s→4s，最多 3 次）；4xx 直接標失敗 |
| 重跑 | 失敗段落可單獨重跑，不重跑已成功的 |
| 成本 | 每次 LLM/TTS 呼叫寫 `usage_log`，記 token / 字數 / 估算費用 |
| 長文本 | 小說可含數十萬字 → 一律先切章節，章節再切段落送 AI；單次請求不超過模型限制 |
| 安全 | Session-based + Spring Security；`/api/**` 需登入；CSRF 開啟 |
| 可觀測 | `job_task` 記錄 job 進度；`usage_log` 記成本 |

## 7. 開發順序

1. `db/migration/V1__init_schema.sql` + `app`/`web` 骨架 + `application.yml` + `WebEnv/docker-compose.yaml`
2. Provider / 模型 / 音色 設定 CRUD（API Key 加密儲存）
3. AI 分析模組（Prompt 契約、JSON 解析與驗證、重試）
4. TTS 合成模組（multi-speaker 分組、PCM 落地、ffmpeg 轉檔、章節合併、ZIP）
5. Thymeleaf 頁面介面 + Security
6. 端到端實測：真實小說 → 分析 → 合成 → 下載音檔

### 7.1 實作階段追加的項目

以下項目在實作過程中追加，不在原始規格內：

| 項目 | 理由 | 對應 |
|---|---|---|
| **資料庫帳號系統** | 對外服務時，設定檔中的明文 `admin/admin` 是實質風險 | `app_user` 表（V4）、BCrypt、`/do-change-password` |
| **Cloudflare named tunnel** | 需要固定公開網址（quick tunnel 每次會變） | systemd user service + 容器化 cloudflared 2026.11.0 |
| **成本記錄** | `usage_log.estimated_cost` 原本只有欄位沒有寫入路徑 | `model_pricing` 表（V5）、`usage.cost` 解析 |
| **TTS 備援模型** | 語音合成失敗會讓整個段落失敗，成本與時間代價高 | `ai_model_setting.fallback_model_id`（V6） |
| **反向代理 HTTPS 處理** | Cloudflare 轉發時 Spring Security 產生的 redirect 降級成 `http://` | `ForwardedHeaderFilter` 明確高優先序 |

### 7.2 對外服務拓撲

```
Telegram 使用者
    ↓ HTTPS
Cloudflare Edge（<your-domain>）
    ↓ named tunnel（QUIC，4 條冗餘連線）
cloudflared 容器 2026.11.0（systemd user service 管理，Restart=always）
    ↓ http://127.0.0.1:8090（host network）
noveltts-app 容器（8090，非 root appuser）
    ↓ JDBC
noveltts-pg 容器（PostgreSQL 17.12）
```

- 應用程式本身只綁 8090（8080 已被 Nextcloud 占用）
- 公開入口只透過 Cloudflare Tunnel，不直接暴露 port
- systemd user service + `loginctl enable-linger eric` → 開機自動啟動、登出後存活
